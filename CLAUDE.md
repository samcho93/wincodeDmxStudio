# Wincode DMX Studio

Browser lighting console (programmer, palettes, cue lists, effects, playbacks). Details: [README.md](README.md).
Sister project: `D:\Work\Web\wincodeMovingHead` (3D simulator; its built-in DMX editor is separate and stays).

## Run
- `npm start` → http://127.0.0.1:7750 (static `web/` + bridge `/ws` → Art-Net 6454 / sACN 5568).
- For a live link with the simulator locally, open it through the simulator's server: http://127.0.0.1:7740/studio/ (same origin → Virtual DMX cable).
- No build. GitHub Pages deploys `web/` as is (`.github/workflows/pages.yml`).

## Layout (`web/js/`)
- `store.js` show file + undo (`store.mark()` before every change, `store.emit(what)` after) · `library.js` fixture profiles · `engine.js` everything that produces DMX · `outputs.js` lines.
- Views: `v-prog.js` (programmer, pools) · `v-patch.js` · `v-cues.js` (cue lists, effects) · `v-out.js` (monitor, setup) · `main.js` (shell, playbacks, command line, keys, MIDI).
- `examples.js` builds the example shows from the profiles.
- Debug: `WDX.engine`, `WDX.store`, `WDX.out`, `WDX.command('1 thru 6 @ 80')`.

## Rules
- Values are stored per fixture and per channel **key** (`{ fixtureId: { key: 0–255 } }`), never per channel number or address.
- Priority in `engine.tick`: defaults → playbacks (intensity HTP × fader, the rest LTP by start order) → effects → programmer → highlight → group masters → grand master / blackout. Keep that order.
- Fixture profiles are data (`web/fixtures/wincode.json`, generated by `npm run import-wincode` from the simulator's models). Do not hand-edit the JSON; change the importer or the model.
- Library fixtures (Open Fixture Library, GDTF): `web/js/lib/*.js` and `web/fixtures/ofl/` are copies from the simulator (`npm run import-library`) — never edit them here. `libimport.js` turns a description into a profile (`profileFromDesc`: base names, heads for repeated colours, attribute groups, ranges). A show keeps the descriptions it uses in `show.library`; `store.opening` registers them; the stage hand-over passes them on as `workspace.library`, so ids, mode ids and channel order must stay those of the description.
- Examples look values up by name in the profiles (colour by range label or RGB / CMY mix, zoom direction from the range text) — no literal channel values for model-specific functions.
- A new transport = a branch in `Outputs.send` (browser side) and, if it needs UDP or a device, in `server/index.js`.
- All user-visible text and code comments are English.
- The Virtual DMX cable protocol is shared with the simulator: `BroadcastChannel('wmh-dmx')`, message `{ t: 'dmx', from, u, data: Uint8Array(512) }`. The stage hand-over writes `localStorage['wmh.stage.v1']`. Change neither without changing the simulator.
